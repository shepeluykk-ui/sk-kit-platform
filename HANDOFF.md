# HANDOFF — передача проекта СК-КИТ

Документ для того, кто продолжает разработку. Описывает то, что не видно из
кода и не покрыто остальной документацией: действующие инварианты, устройство
владения задачами анализа, фактически проверенное состояние, открытые дефекты и
подводные камни, на которые уже наступали.

Состояние на коммит, которым добавлен этот файл. Сведения ниже получены
измерениями, а не чтением кода; там, где проверка не выполнялась, это сказано
прямо.

---

## 1. Что это за система

ЕИС «Строительный контроль» — учёт строительного контроля: проекты, дефекты,
предписания, исполнительная документация (АОСР), сметы (КС-2/КС-3), графики,
инспекции, аудит действий. Поверх этого — многоагентный AI-анализ проектной
документации, формирующий управленческий отчёт.

Стек: Node.js 24 + Express + TypeScript на сервере, React 19 + Vite на клиенте,
SQLite через встроенный `node:sqlite`, LangGraph для оркестрации AI-агентов,
Capacitor для мобильной сборки.

### Главный принцип проекта

Он задан в `CLAUDE.md` и его стоит прочитать до первой правки. Коротко:

```
СНАЧАЛА ДОКАЗАТЬ → ПОТОМ ИЗМЕНИТЬ → ПОТОМ ПРОВЕРИТЬ
```

Нельзя исправлять предполагаемую причину и нельзя объявлять задачу решённой на
основании того, что код выглядит правильным. Каждое существенное утверждение
маркируется: `ПОДТВЕРЖДЕНО` · `ПОДТВЕРЖДЕНО ЧАСТИЧНО` · `НЕ ПРОВЕРЕНО` ·
`ЛОЖНОЕ СРАБАТЫВАНИЕ` · `ПРЕДПОЛОЖЕНИЕ`.

## 2. База данных: что именно используется

**Используется SQLite через `node:sqlite`.** Файл — `process.cwd()/data/skkit.db`,
схема создаётся при старте в `src/server/database.ts`.

PostgreSQL-ветка в коде **существует, но не подключена**: все синхронные вызовы
(`dbUpsert`, `dbLoadAll`, `dbExists`, …) бросают исключение при `isPostgres`, а
их асинхронные варианты не вызывает никто. Поэтому `initDatabase()` намеренно
**отказывается стартовать**, если задан `DATABASE_URL`, — иначе сервер поднялся
бы и упал на первом же обращении к базе.

Отсюда следствия:

- `docker-compose.yml`, `init-db.sh`, `POSTGRES_SETUP.md`, `QUICKSTART_POSTGRES.md`,
  `UPDATE_ENV_FOR_POSTGRES.txt`, `start-postgres-dev.ps1` относятся к
  **неподключённой** ветке. Их наличие не означает, что приложение работает на
  PostgreSQL;
- переход на PostgreSQL — это миграция 70+ мест вызова, а не смена переменной
  окружения;
- не включайте `DATABASE_URL` «чтобы заработал Docker Compose»: сервер откажется
  стартовать с внятным сообщением, и это правильное поведение.

**Node 24 обязателен.** `src/server/database.ts` импортирует `node:sqlite` на
верхнем уровне модуля. В Node 20 такого встроенного модуля нет вовсе
(`ERR_UNKNOWN_BUILTIN_MODULE`), и перехватить это нельзя — ошибка возникает при
загрузке. Минимум зафиксирован в `package.json` → `engines.node`:
`>=24.19.0 <25.0.0`. `Dockerfile` обеих стадий — `node:24-alpine`. Понижение
версии ломает приложение полностью.

## 3. Владение задачами AI-анализа

Самая тонкая часть системы. Задача анализа живёт минутами, выполняется в
процессе сервера и не имеет контрольных точек. Нужно было одновременно: не дать
двум процессам исполнять одну задачу, не дать проекту зависнуть навсегда и не
уничтожить работу живого процесса.

### Модель

Таблица `ai_analyses`, помимо `data` (весь объект задачи в JSON), несёт
отдельные колонки:

| Колонка | Смысл |
|---|---|
| `status` | вынесен из JSON наружу, потому что по нему строится индекс |
| `owner_id` | какой экземпляр приложения исполняет задачу (`INSTANCE_ID`) |
| `lease_until` | до какого момента владение действительно |

`INSTANCE_ID` уникален для запуска процесса. `ANALYSIS_LEASE_MS = 60_000` —
срок владения; нижняя граница задана таймаутом обращения к модели (15 с) с
четырёхкратным запасом.

Активными считаются шесть статусов: `QUEUED`, `PARSING`, `EXTRACTING`,
`ANALYZING`, `CALCULATING`, `VALIDATING`. Этот перечень — **единственный
источник истины**: он же подставляется в предикат частичного уникального
индекса. Расхождение между кодом и схемой означало бы, что приложение и база
считают активность по-разному.

### Инварианты, которые нельзя нарушать

**И1. Один проект — не более одного активного анализа.** Держится не кодом, а
базой:

```sql
CREATE UNIQUE INDEX ux_ai_analyses_one_active_per_project
  ON ai_analyses(project_id) WHERE status IN (<шесть активных статусов>)
```

Прикладная проверка в `createAndRunAnalysis` стоит до первого `await`, поэтому
для однопоточного цикла событий блок «проверить и вставить» атомарен. Но
полагаться только на неё нельзя — индекс ловит и то, что прошло в обход.

**И2. Процесс B не уничтожает живую задачу процесса A.** Восстановление берёт
только брошенные задачи: без владельца либо с истёкшим сроком. До этого
восстанавливались все активные, и второй экземпляр на той же базе объявлял
прерванной задачу, которую прямо сейчас исполнял живой процесс: тот продолжал
работу, запись уходила в `FAILED`, освободившийся индекс позволял запустить
второй конвейер, а первый затем падал на нарушении уникальности, теряя готовый
результат.

**И3. Процесс, потерявший владение, не продолжает управлять задачей.**
`dbUpdateAnalysisJob` условен: `WHERE id = ? AND (owner_id IS NULL OR
owner_id = <мой> OR lease_until IS NULL OR lease_until < now)`. Возвращает
признак записи; `persist()` при неудаче бросает `ANALYSIS_OWNERSHIP_LOST` и
конвейер прекращается, не затирая состояние, выставленное тем, кто задачу
восстановил.

**И4. База — источник истины, память — только кэш.** `analysisJobsStore` (Map)
остаётся рабочей копией выполняющегося конвейера: он мутирует объект чаще, чем
пишет в базу. Но читающие методы сверяют кэш с базой (`resolveJob`): кэш
применим **только** если база подтверждает, что задача активна и её владелец —
этот процесс. Иначе отдаётся строка базы, а запись из памяти удаляется. Без
этого прежний владелец продолжал отвечать `PARSING` после того, как другой
процесс перевёл задачу в `FAILED`, — и по этому ответу создавался второй
конвейер того же проекта.

**И5. Брошенная задача подбирается всегда, а не только при старте.**
`startRecoverySweep()` работает периодически, с интервалом
`ANALYSIS_LEASE_MS / 2`. Отдельной настройки периода нет намеренно — вторая,
независимо настраиваемая модель времени означала бы рассинхронизацию. Ревизия
только при старте закрывала лишь медленный перезапуск: если процесс поднимался
быстрее срока владения (обычное поведение systemd, pm2, `docker restart`),
задача мёртвого владельца при старте ещё не выглядела брошенной, а после
истечения срока её уже никто не проверял — проект оставался заблокирован
индексом навсегда.

**И6. Восстановление завершает задачу, а не возобновляет её.** `executePipeline`
— единая функция без контрольных точек: промежуточного состояния для
продолжения не существует. Перезапуск тоже исключён — он обратился бы к платной
модели без ведома пользователя. Поэтому брошенная задача переводится в `FAILED`
с текстом «Анализ прерван остановкой сервера и не был возобновлён. Запустите
анализ заново», владение снимается, проект разблокируется. Это осознанное
решение, а не недоработка.

**И7. Штатная остановка не отдаёт работу раньше времени.** При `SIGTERM`/`SIGINT`
процесс прекращает приём новой работы, останавливает периодические таймеры,
закрывает соединения и базу, выходит с кодом 0 — но **владение не снимает**.
Снятие сделало бы выполняющуюся прямо сейчас задачу добычей другого процесса
немедленно. Задача остаётся за ушедшим процессом до истечения срока и затем
подбирается ревизией — тот же путь, что и после аварийной остановки. Семантика
одна для обоих случаев.

### Устойчивость к занятой базе

Подтверждение владения (`startLeaseHeartbeat`, период 15 с) пишет в базу из
таймера. Раньше исключение оттуда было необработанным, и любой второй писатель
— резервное копирование, административная сессия, второй экземпляр — завершал
процесс-владелец с кодом 1, то есть отказ наступал именно в той конфигурации,
ради которой владение и вводилось.

Сейчас различаются два случая (`isTransientDbContention`): временная занятость
(`SQLITE_BUSY`, `SQLITE_LOCKED`, «database is locked») проходит сама, повтор
уместен, следующее срабатывание таймера повторит попытку, запас срока
вчетверо больше периода. Прочие ошибки — повреждение файла, ошибка в запросе —
повтором не лечатся, их нельзя ни скрывать, ни принимать за нехватку доступа:
они логируются отдельно и с полным текстом.

### API-ответы

- `POST /api/projects/:projectId/ai-analysis` → `201` при создании;
  **`409`** если у проекта уже есть активный анализ (идентификатор чужой задачи
  в ответе не раскрывается); **`503`** с `Retry-After` если база временно занята
  или процесс останавливается. `409` и `503` — разные состояния, не путать;
- `GET /api/projects/:projectId/ai-analysis` → состояние из базы;
  `?analysisId=` проверяется на принадлежность проекту, иначе параметр
  игнорируется и пишется запись аудита `DENIED` (это закрытый IDOR).

## 4. Тесты: как запускать и почему именно так

```bash
npm run lint              # tsc --noEmit
npm run build             # vite build + esbuild -> dist/server.cjs
npm test                  # 5 наборов, не требующих заранее поднятого сервера
npm run test:security     # нужен уже запущенный сервер
npm run test:e2e          # нужен уже запущенный сервер
```

`npm test` — это последовательно `test:orchestrator` (37), `test:rt002` (5),
`test:rt003` (5), `test:r3013` (3), `test:r30131` (16). Последовательно, а не
параллельно: все они занимают порт 3000.

### Подводный камень: наборы взаимно загрязняют состояние

`test:security` и `test:e2e` **нельзя запускать подряд на одном экземпляре
сервера**. Проверено опытом: второй по порядку всегда падает — `e2e` даёт 22/25
после `security`, `security` даёт 62/64 после `e2e`, тогда как на чистом
экземпляре каждый проходит полностью (64/64 и 25/25). Каждому нужен свой
сервер с чистой базой; в CI это организовано отдельными песочницами
(`mktemp -d`) под каждый набор.

### Подводный камень: PID фонового сервера

При запуске сервера из подоболочки (`( ... & echo $! )`) переменная `$!` не
даёт PID самого процесса, и остановить его не удаётся: следующий набор идёт
против прежнего экземпляра с уже загрязнённой базой. В CI используется
`( cd … && exec node … ) &` — `exec` замещает подоболочку процессом, поэтому
`$!` указывает на него.

### Подводный камень: Windows не доставляет SIGTERM

На win32 `child.kill('SIGTERM')` доходит до `TerminateProcess`, и обработчик не
вызывается — процесс исчезает мгновенно. Это установлено замером: отдельный
процесс с заведомо корректным обработчиком не успевает о себе сообщить.
Поэтому сценарий `D6 SIGTERM` в `test:r30131` на Windows помечается
`НЕ ПРОВЕРЕНО` (15/16) и **не** засчитывается как пройденный, а на Linux
исполняется и даёт 16/16. Если вы работаете на Windows — это не дефект, но и
не доказательство: проверяйте graceful shutdown на Linux или в контейнере.

### Фактические результаты последнего прогона CI (Linux, Node 24)

```
Typecheck                                 0 ошибок TS
Build                                     dist/server.cjs 346.4 kB
npm test                                  37/37 · 5/5 · 5/5 · 3/3 · 16/16
test:security                             64/64
test:e2e                                  25/25
```

Итого 155 тестов, все пройдены. `ПОДТВЕРЖДЕНО` фактическим прогоном
GitHub Actions.

## 5. Запуск

```bash
npm install
```

Перед первым запуском задайте пароль seed-пользователей в `.env` (шаблон —
`.env.example`):

```
SEED_USER_PASSWORD=<ваше значение>
```

Без него: в dev-режиме пароль генерируется случайно, печатается в консоль один
раз и меняется при каждом перезапуске; при `NODE_ENV=production` сервер
**отказывается стартовать**. Все seed-пользователи используют один пароль.
Логины — в `src/data/initialData.ts`, основные: `admin@stroycontrol.pro`
(SUPER_ADMIN), `admin@kit-sk.ru` (ADMIN).

```bash
npm run dev       # разработка: tsx + vite middleware
npm run build && npm start   # production-режим
```

## 6. Контейнер

`Dockerfile` — двухстадийный, `node:24-alpine` на обеих стадиях.

- `dumb-init` как PID 1 — корректная доставка сигналов;
- `VOLUME ["/app/data", "/app/uploads"]` — без этого пересоздание контейнера
  уничтожило бы базу с задачами, владением и аудитом, и загруженные документы;
- `USER node` — приложению права root не нужны, каталоги данных переданы ему
  через `chown`;
- `HEALTHCHECK` обращается к `/api/health`. **Это liveness, а не readiness**:
  проверяет, что процесс отвечает, но не готовность к работе. Если
  orchestration потребует readiness — это отдельная задача.

`Статус: НЕ ПРОВЕРЕНО.` Образ ни разу не собирался и контейнер не запускался:
Docker runtime не был доступен. Все перечисленные свойства установлены
статическим разбором. Graceful shutdown проверен **вне контейнера** на Linux-ядре
(см. §4), контейнерный слой этим не подтверждён.

## 7. CI/CD

`.github/workflows/deploy.yml`, триггеры — `push`/`pull_request` в `main` и
`master`.

| Job | Условие | Содержание |
|---|---|---|
| `build-and-test` | безусловно | typecheck, сборка, проверка артефакта, `npm test`, HTTP-наборы (каждый на своём чистом сервере) |
| `security-scan` | безусловно | Snyk |
| `docker-build` | `main` + задан `AWS_ROLE_ARN` | сборка образа и публикация в ECR |
| `deploy-to-ecs` | `main`, push, задан `AWS_ROLE_ARN` | обновление сервиса ECS |
| `notify-slack` | задан `SLACK_WEBHOOK` | уведомление |

### Чего не делать

**Не возвращайте `|| true` и `continue-on-error` на проверки.** Раньше здесь
стояло `npm run lint 2>/dev/null || true` и `npm test 2>/dev/null || true`,
причём скрипта `test` не существовало вовсе: вывод уходил в `/dev/null`, код
возврата подменялся успехом, и job оставался зелёным при любых ошибках. Это
хуже отсутствия CI — такой «зелёный» ни о чём не говорит.

**Не условьте jobs по `secrets`.** Контекст `secrets` недоступен в выражении
`jobs.<id>.if` (там работают только `github`, `needs`, `vars`). Попытка так его
использовать приводит к тому, что workflow не проходит валидацию и прогон
завершается как `failure`, **не создав ни одного job** — на это уже наступали.
Проверка наличия секрета делается первым шагом внутри job, где `secrets`
доступны, с записью результата в `GITHUB_OUTPUT`.

**Не добавляйте в `.gitignore` правила вида `/src/*`, `/tests/*`, `/docs/`.**
В прежнем репозитории они приводили к тому, что новые файлы кода молча не
попадали в коммит: отсутствовали `src/server/genaiCircuitBreaker.ts` и
`src/data/initialData.ts`, и CI падал на typecheck с `TS2307`. Причём локально
всё собиралось — файлы лежали на диске.

**Записывайте правила каталогов с ведущим слешем.** Шаблон `data/` без слеша
матчит одноимённый каталог на любом уровне: вместе с корневым `data/` (база
SQLite) исключался и `src/data/`. Отсюда `/data/`, `/uploads/`, `/dist/`,
`/logs/`, `/tmp/`, `/build/`, `/out/`, `/coverage/`, `/backups/`.

## 9. Журнал фактических ошибок

Это главный раздел документа. Ниже — ошибки, которые действительно были
допущены при работе над проектом, с истинными причинами. Почти каждая выглядела
как «код правильный», и почти каждая вскрылась только измерением. Если вы
продолжаете работу — не повторяйте их.

### 9.1 Неверно угаданный API вместо прочитанного

`src/server/database.ts` был переписан под API `sql.js`
(`stmt.step()`, `getAsObject()`, `free()`), которого в `node:sqlite` не
существует. Сервер перестал загружаться целиком.

**Причина:** API не был проверен, он был предположен по аналогии с другой
библиотекой. **Правильно:** `node:sqlite` использует `.all()`, `.get()`,
`.run()`. **Урок:** API смотрят в рантайме или документации, а не по памяти о
похожей библиотеке.

### 9.2 Ложноположительная проверка запуска

Проверка «сервер поднялся» была сделана через `await import()` модуля. Импорт
завершался успешно **раньше**, чем падала асинхронная `startServer()`, и
проверка показывала успех при нерабочем сервере.

**Урок:** факт работы сервера подтверждается HTTP-запросом к живому эндпоинту,
а не успешной загрузкой модуля.

### 9.3 Тест, построенный под собственную реализацию

Для фикса R3-013 были написаны тесты, которые прошли 3/3 — и не доказывали
ничего. Сценарий «мёртвый владелец» искусственно просрочивал владение **до**
старта второго процесса, то есть моделировал только медленный перезапуск.
Сценарий «живой владелец» опирался на `EADDRINUSE` (занятый порт), а не на
механизм владения. Независимая проверка нашла, что при быстром перезапуске
проект блокируется навсегда — ровно тот случай, который тест обходил.

**Урок:** тест, написанный после реализации тем же человеком, склонен
проверять заложенную последовательность, а не требование. Формулируйте
сценарий от требования («что будет при перезапуске через секунду»), а не от
кода.

### 9.4 Шесть дефектов внутри собственного исправления

Исправление R3-013 (владение задачами) само внесло: блокировку проекта навсегда
при быстром перезапуске; падение процесса-владельца от необработанного
`SQLITE_BUSY` в таймере; расхождение кэша и базы после восстановления;
отсутствие фенсинга владельца в `dbUpdateAnalysisJob`; выдачу `500` вместо
осмысленного кода при гонке; отсутствие graceful shutdown.

**Урок:** введение механизма координации (владение, аренда, таймеры) создаёт
новый класс отказов — гонки, устаревшее состояние, падения в фоновых задачах.
Каждый такой механизм требует отдельного набора сценариев, а не одного
«счастливого пути». См. И1–И7 в §3.

### 9.5 Утверждения, оказавшиеся неверными

Трижды были сделаны уверенные заявления, опровергнутые измерением:

- «в проекте 73 ошибки TypeScript во фронтенде» — на момент проверки
  `npm run lint` давал **0** ошибок, exit 0;
- «CI упадёт на `node:sqlite`» — нет: сборка не исполняет артефакт, а тесты
  были замаскированы `|| true` и не запускались вовсе. Расхождение версий было
  реальным, но следствие — другим;
- «graceful shutdown работает» (до проверки на Linux) — на Windows обработчик
  не вызывается вообще, и проверка была невозможна.

**Урок:** маркируйте утверждения (`ПОДТВЕРЖДЕНО` / `НЕ ПРОВЕРЕНО`) и
перепроверяйте перед тем, как на них опираться. Состояние проекта меняется:
то, что было верно вчера, сегодня может быть ложным.

### 9.6 Правила `.gitignore`, молча терявшие код

**Дважды** файлы исходного кода не попадали в публикацию, и оба раза локально
всё собиралось — файлы лежали на диске:

1. правило `/src/server/*` исключило новый `src/server/genaiCircuitBreaker.ts`.
   CI упал: `TS2307 Cannot find module`;
2. правило `data/` **без ведущего слеша** матчит одноимённый каталог на любом
   уровне — вместе с корневым `data/` исключился `src/data/`, и пропал
   `src/data/initialData.ts`. CI упал так же.

**Уроки:** не исключайте каталоги с исходным кодом целиком; записывайте правила
каталогов с ведущим слешем (`/data/`, не `data/`); после изменения `.gitignore`
проверяйте публикуемый состав **клоном в чистый каталог** и сборкой в нём, а не
локальной сборкой — локально файл есть, в репозитории его нет.

### 9.7 Маскировка проверок в CI

В workflow стояло `npm run lint 2>/dev/null || true` и
`npm test 2>/dev/null || true`, причём скрипта `test` в `package.json` **не
существовало**. Вывод уходил в `/dev/null`, код возврата подменялся успехом.
Job был зелёным при любых ошибках, а тесты не запускались ни разу.

**Урок:** зелёный CI, который не может покраснеть, хуже отсутствия CI — он даёт
ложную уверенность. Проверяйте, что пайплайн действительно падает при внесённой
поломке.

### 9.8 Контекст `secrets` в условии job

Попытка условить jobs по `secrets.AWS_ROLE_ARN != ''` сломала workflow целиком:
прогон завершился как `failure`, **не создав ни одного job** (`jobs: 0`,
`created_at` = `updated_at`).

**Причина:** в выражении `jobs.<id>.if` доступны только контексты `github`,
`needs`, `vars`. `secrets` — нет. **Правильно:** проверять секрет первым шагом
внутри job и писать результат в `GITHUB_OUTPUT`.

### 9.9 Тестовые наборы, мешающие друг другу

Скрипт, запускавший `test:security && test:e2e` на одном сервере, давал
стабильный отказ второго набора. Сначала это выглядело как регрессия кода.

**Причина:** наборы взаимно загрязняют состояние базы; на чистом экземпляре
каждый проходит полностью. Отдельно: `$!` из подоболочки не давал PID сервера,
старый экземпляр продолжал слушать порт, и следующий набор шёл против
загрязнённой базы — результаты 23/64 и 0/25 были артефактом обвязки, а не кода.

**Урок:** прежде чем объявлять падение регрессией, проверьте изоляцию
окружения. И убедитесь, что предыдущий процесс действительно умер.

### 9.10 Несовместимость базового образа

`Dockerfile` был на `node:20-alpine`, тогда как артефакт содержит
`require("node:sqlite")` на верхнем уровне. Образ собирался, контейнер падал
сразу после старта.

**Как установили:** запустили оба рантайма и сравнили —
Node 20.19.0 даёт `ERR_UNKNOWN_BUILTIN_MODULE`, Node 24.19.0 возвращает модуль.
**Урок:** совместимость рантайма проверяется запуском рантайма, а не чтением
списка зависимостей.

### 9.11 Метод, который себя оправдал

Четыре раза независимая проверка находила обход там, где задача считалась
закрытой: дважды по подмене данных в AI-ответах, один раз по персистентности
задач, один раз по владению. Каждый раз исполнителем был тот же код, который
«выглядел правильным».

Что работает:

- **воспроизводить среду, а не рассуждать о ней.** Сборка в чистом клоне, запуск
  на целевой ОС, настоящий сигнал вместо вызова функции напрямую;
- **отделять ограничение среды от дефекта.** «Windows не доставляет SIGTERM» —
  это `НЕ ПРОВЕРЕНО`, а не `PASS`. Пропуск с объяснением честнее зелёной
  галочки;
- **доказывать причину до правки.** В журнале выше почти каждая вторая запись —
  исправление не той причины, которая казалась очевидной;
- **проверять фикс сценарием, который падал до него.** Если тест проходит и до
  исправления — он проверяет не то.

## 10. Чего в репозитории намеренно нет

- `.env` — реальные секреты. Шаблон: `.env.example`;
- `data/` — рабочая база SQLite. **Содержит записи реального пилотного объекта
  (AERON).** Не перезаписывайте и не используйте для деструктивных тестов: для
  проверок создавайте изолированные базы в отдельном рабочем каталоге;
- `uploads/` — загруженные документы;
- `dist/`, `node_modules/` — артефакты;
- `.claude/` — инструментарий Claude Code, к коду проекта не относится.
  Рабочий регламент остался в `CLAUDE.md`.

## 11. С чего начать

1. Прочитать `CLAUDE.md` — рабочий регламент, он обязателен и объясняет, почему
   в этом проекте не принимают «код выглядит правильно» за доказательство.
2. Прочитать §3 этого документа — владение задачами самое неочевидное место, и
   в нём уже было четыре отдельных дефекта.
3. `npm install`, задать `SEED_USER_PASSWORD` в `.env`, `npm run dev`.
4. Прогнать `npm run lint`, `npm run build`, `npm test` — убедиться, что
   окружение рабочее, прежде чем что-то менять.
5. Для правок в области анализа: любое изменение проверять наборами
   `test:rt002`, `test:rt003`, `test:r3013`, `test:r30131` — они закрывают
   инварианты И1–И7 и ловят именно те регрессии, на которые уже наступали.
